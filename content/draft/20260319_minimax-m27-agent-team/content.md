# MiniMax M2.7 母稿（第二版）

MiniMax M2.7 刚发布时，最容易写的角度其实很明确：它又变强了，它又往 GPT、Claude、Gemini 这些头部模型靠近了一步。

这个角度当然没错，但我看完资料之后，觉得它不是这次最值得写的点。

我现在更想写的是另一件事：**M2.7 这次真正有信号量的地方，不只是能力提升，而是它展示出来的能力，越来越适合被放进一个需要持续协作、持续纠偏、持续收敛的系统里。**

我先把这个判断为什么成立说清楚。

## 先看哪几条事实真的重要
第一条，MiniMax 官方明确说，M2.7 已经被用进了它自己的 RL 研发流程里，而且它能处理 **30%-50% 的工作流**。这里不是一句抽象的“参与研发”，官方给出来的内容很具体：文献回顾、跟踪实验 spec、管理数据和 artifact、启动实验、监控进度、读日志、debug、分析指标、修代码、提 merge request、跑 smoke test。

这条信息为什么重要？因为它说明 M2.7 展示的不是“会回答研究问题”，而是“已经能在一个真实工作流里承担一串连续任务”。如果它只是写一段代码、回答一个问题，那还只是强模型的常规叙事；但现在它开始碰的是调度、监控、修正和推进，这些能力天然更靠近系统层，而不是单次回答层。

第二条，MiniMax 还给了一组更能说明问题的测试：他们让 M2.7 围绕一个 internal scaffold，反复执行“分析失败轨迹、计划修改、改 scaffold、跑评测、对比结果、决定保留还是回滚”的循环，连续跑了 **100 多轮**。在另一组更公开的 MLE Bench Lite 测试里，M2.7 做了三次 **24 小时自主迭代**，最后最好的一次拿到 **9 金 5 银 1 铜**，三次平均奖牌率 **66.6%**。

这组数字为什么比普通 benchmark 更值得看？不是因为 66.6% 这个数字本身多漂亮，而是因为它说明模型在长时间运行里没有很快崩掉，也没有只靠一次性灵感吃饭。它需要靠短期记忆、自我批评和下一轮修正把任务往前推。也就是说，这里考的已经不是“会不会答”，而是“能不能在一个很长的闭环里持续推进”。

第三条，M2.7 这次最能支撑它“适合进系统”的，不只是研发闭环案例，还有稳定性指标。公开材料里有一条我觉得比很多跑分更值得留：在 **40 个复杂 skills**、每个 skill 定义都超过 **2000 tokens** 的环境里，M2.7 还能保持 **97% 的 skill adherence**。

这条数据为什么重要？因为很多模型不是不会做，而是到了复杂环境里容易乱调工具、乱传参数、跑偏流程。97% 这个数字的意义，不是说明它“更聪明”，而是说明它在多约束环境里更稳，比较适合放到复杂系统里工作。

第四条，M2.7 这次的软件工程成绩也值得看，但不是所有分数都值得写进正文。我觉得真正应该留下来的，只有那些能支撑“它适合复杂闭环任务”的数据，比如：
- **SWE-Pro 56.22%**
- **Terminal Bench 2 57.0%**
- **VIBE-Pro 55.6%**

这几个分数的共同点，不是单纯证明“代码能力强”，而是更接近真实工程里的长链路任务、系统理解和项目交付。尤其是 Terminal Bench 2 这种偏系统理解的指标，和前面那些研发闭环、自主迭代、自我修正的材料放在一起看，才能共同说明一件事：MiniMax 这次想证明的，不只是模型更强，而是它更像一个能被放进复杂系统里跑起来的模型。

## 所以，为什么我会觉得这次更值得看的，是“组织智能”
前面这些事实如果只单独看，当然也可以被解释成“模型更强了”。

但它们放在一起的时候，会指向一个更具体的判断：M2.7 这次最值得看的，不是单点回答能力，而是它越来越适合进入那种需要多步骤协作、持续反馈、持续修正的系统。

这里我为什么会用“组织智能”这个词？不是为了拔高，而是因为这些证据都在说明同一件事：

- 它不是只做单步输出，而是在参与一串连续动作
- 它不是只给答案，而是要看反馈、读日志、修正策略
- 它不是只会跑一个流程，而是要在长链路里维持收敛
- 它不是只靠 prompt 一次性写漂亮话，而是更适合进入带约束、带工具、带状态变化的系统

换句话说，前面那些数字真正说明的，不是“模型更聪明”，而是“模型更适合被组织起来工作”。

这也是为什么我觉得，这次只写“又追近了谁”有点可惜。因为真正有新意的，是它开始更明确地跨进了系统层。

## Kimi 和 MiniMax 的对比，应该怎么写才稳
我还是觉得那个画面是对的：**Kimi 像流水线团队，MiniMax 像战术小队。**

但这句话要写得稳，必须加一个前提：它说的是**当前更鲜明的产品范式差异**，不是绝对能力边界。

为什么我会把 Kimi 理解成更像流水线？因为 Kimi2.5 Agent Swarm 给人的核心感觉是并发、分发、稳定编排。它更像是在回答：任务怎么拆、怎么并发、怎么尽量别出错。这套思路天然适合标准化、可拆解、重吞吐的任务。

为什么我会把 MiniMax 理解成更像战术小队？因为 M2.7 这次真正拿出来的材料，重点都不是“并发规模”，而是角色分配、自我批评、复杂环境里的 skill 遵循、长链路任务收敛，以及真实研发闭环里的补位和修正。它更像是在回答：在复杂任务里，这个系统能不能自己查漏、纠偏、把事情继续往前推。

这两个方向，我觉得现在都成立。但不能写太满。更稳妥的说法不是“Kimi 只能做流水线，MiniMax 只能做小队”，而是：**Kimi 当前更鲜明的优势在于并发组织和稳定编排，MiniMax 当前更鲜明的优势在于复杂任务里的闭环推进和协作收敛。**

## 对普通用户，这到底意味着什么
这里其实不需要讲太玄。

普通用户真正关心的，还是很朴素的三个问题：
- 交给你会不会翻车
- 我没想到的地方你能不能补上
- 我到底该把你当执行工具，还是协作伙伴

如果把这个差异翻成人话，我觉得还是那句最有用：

**你最怕出错，就更适合用像流水线的系统；你最怕漏想，就更适合用像小队的系统。**

这句话的好处是，它不是空洞概括，而是真的能指导任务分配。

比如标准化整理、固定格式交付、规则明确的流程任务，优先级通常是稳，不是巧。这种时候，更像流水线的系统更有价值。

但如果是复杂研究、debug、方案推演、边做边修的任务，真正稀缺的就不是执行，而是补位。这种时候，更像战术小队的系统会更有意思。

## 那“国内开始进入前沿”这句话，到底该怎么写
这一点我觉得上一版确实写得太快了。

更稳的说法，不应该是“国内模型已经进入前沿”，更不应该是“国内模型已经领先”。

目前资料最多能支撑到什么程度？我觉得只能支撑到这一步：**国内模型在多智能体组织方式这件事上，已经开始拿出比较明确的方法路线，而且这件事很值得重点观察。**

为什么我会这么说？因为至少现在已经能看到几条不一样的路：
- Kimi 在做并发型、蜂群型的 agent 组织
- MiniMax 在做更强调 team、角色边界、结果验证和收敛的组织方式
- 智谱也在围绕 OpenClaw / 龙虾这种真实长链路执行场景，去做更偏稳定执行和时间维度的专项优化

这些还不足以支撑“全面前沿”这样的结论，但足以支撑另一个更稳的判断：**国内团队不只是追单点能力，也开始在“怎么组织一群 AI 干活”这件事上形成自己的方法路线。**

这句话我觉得更站得住。

## 我现在的结论
所以如果现在让我重新收一句话，我会这么说：

MiniMax M2.7 这次最值得看的，不只是它作为一个新发布模型又变强了，而是它拿出了一批更像系统层证据的东西：真实研发工作流参与、长时间自主迭代、复杂环境下的 skill 遵循、以及更接近复杂工程任务的 benchmark 表现。把这些放在一起看，它真正让人觉得有意思的地方，不是“又一个强模型”，而是“它越来越像一个能被放进复杂系统里持续工作的模型”。

这也是为什么我觉得，接下来比单纯追排行榜更值得继续看的，是另一条线：

**谁更会把智能组织起来。**

这条线，我后面会继续写。
