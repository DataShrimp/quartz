# 为什么很多 AI 项目卡在生产前？核心不是能力，而是边界设计

先说结论：

**能力决定上限，边界决定能不能上生产。**

我这段时间看了不少团队做 AI Agent，发现一个非常稳定的失败模式：

- 前期把精力都放在“模型能力展示”
- 中期开始遇到幻觉、越权、结果不稳定
- 后期才补权限、审批、回滚、审计
- 最后项目停在“能演示，难上线”

这不是某个模型的问题，是系统设计顺序的问题。

## 1）为什么“能力优先”会失败？

因为生产环境最怕的不是“偶尔做不出来”，而是“做错且不可控”。

在真实业务里，风险来自三类不确定性：
1. **行为不确定**：同样输入，输出波动大
2. **权限不确定**：越过预期边界执行动作
3. **责任不确定**：出了问题无法定位链路

如果这三件事没被工程化处理，模型能力越强，潜在破坏面反而越大。

## 2）“数字员工系统”和“AI工具”有什么本质区别？

工具思维：
- 关注功能列表（会什么）
- 关注速度和成本

系统思维：
- 先定义岗位职责（该做什么）
- 再定义禁区（绝不能做什么）
- 然后定义流程闭环（谁审批、谁复核、谁验收）

这就是为什么我更倾向用“数字员工系统”而不是“AI提效工具”这个说法。

## 3）用 OpenClaw 怎么落地这个思路？

以 OpenClaw 为例，真正值得用的不是“接了多少模型”，而是这些工程能力：

- 会话与角色可分离（不同任务不同职责）
- 工具调用可约束（敏感动作可审批）
- 全链路有日志（能审计、能回放）
- 配置可版本化（能复用、能回滚）

换句话说，重点是把“边界和流程”写进系统，而不是靠人记住规则。

## 4）一个可执行的最小闭环

建议从一个小场景起步，不要一上来全自动：

**步骤 A：禁区清单**
- 明确哪些操作必须人工确认
- 明确哪些数据不可外发

**步骤 B：岗位分工**
- 产出 Agent
- 复核 Agent / 人工复核
- 验收节点

**步骤 C：验收标准**
- 结果格式
- 事实校验方式
- 失败处理与重跑机制

当这三步稳定后，再扩展场景。

## 5）真正该讨论的问题

我们总在问“哪个模型更强”，
但对业务更关键的问题是：

- 这套系统能否稳定交付？
- 出错后是否可追责、可回滚？
- 新人接手后是否还能跑？

如果这些问题没有答案，项目的天花板不在模型，而在治理。
